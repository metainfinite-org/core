dag-cbor vs DRISL
    DRISL (Deterministic Representation for Interoperable Structures and Links) is a deterministic CBOR profile under the DASL (Data Addressed Structures and Links) specification that serves as the successor to DAG-CBOR in ecosystems like the AT Protocol (Bluesky). Both are constrained, deterministic subsets of CBOR that enforce canonical byte representations so identical data produces identical hashes/CIDs, and both use CBOR Tag 42 for content-addressed links.
    == Key Differences & Relationship
    • Origin & Ecosystem: DAG-CBOR originates from IPLD as a codec for the IPLD Data Model. DRISL comes from DASL—a web-friendly, interoperable subset of IPFS/IPLD primitives—and is used by the AT Protocol as the successor to DAG-CBOR.
    • Specification & Stability: DRISL is designed as a strict, well-defined profile anchored to core CBOR features with explicit normalization and decoding constraints to avoid ambiguities across implementations and libraries.
    • Shared Foundations: Both require deterministic encoding (such as shortest integer encoding, definite lengths, and sorted map keys), restrict map keys to strings, and rely on Tag 42 for compact binary CID links while remaining readable as standard CBOR.

ipfs multihash
    An IPFS multihash is a self-describing cryptographic hash format that embeds metadata—specifically the hashing algorithm used and the byte length of the digest—directly into the hash value itself.
    Because IPFS relies on content-based addressing, multihashes future-proof the network against cryptographic obsolescence. If an algorithm like SHA-256 is ever compromised, IPFS can smoothly transition to a newer algorithm without breaking existing links or changing how identifiers are parsed.

Open design questions for the demo
- Authentication: since identities are just integers and everything is centralized, do you want real signatures (users sign events with keys) or just trust the server and pass a user id? Signing is closer to the real system but adds work.
- Type schemas: does a "new type" event carry a schema (e.g. JSON Schema) that the server validates payloads against, or are payloads free-form in the demo?
- Bootstrap: the first type event needs a type to be typed by. A self-referential "type of types" event is the usual answer.
