Views composed of views. Yes, composition is unavoidable, and you'd be building a layout engine. Reuse what exists rather than inventing one. The proven shape is a component tree: each view has props (parameters like the selected node) and children (other views, referenced by address), data comes from bound queries, and layout uses flexbox/grid semantics (stack, row, grid). Existing declarative UI specs worth studying are Adaptive Cards, Retool/Appsmith-style JSON configs, and Notion's block model. Render with React from a small whitelist of blocks (list, tree, graph, form, button, text, stack/row).

Open design questions for the demo
- Authentication: since identities are just integers and everything is centralized, do you want real signatures (users sign events with keys) or just trust the server and pass a user id? Signing is closer to the real system but adds work.
- Type schemas: does a "new type" event carry a schema (e.g. JSON Schema) that the server validates payloads against, or are payloads free-form in the demo?
- Bootstrap: the first type event needs a type to be typed by. A self-referential "type of types" event is the usual answer.
